# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

DSView — a real-time, multi-asset trading data pipeline (Kafka, Spark Structured Streaming, FastAPI) with custom volume footprint, whale tracking, and technical indicators.

`ingestion/`, `streaming/`, `storage/`, `backend/`, `alerts/`, `backfill/` and `frontend/` all have real implementation: live Binance trades → Redpanda → Spark → Redis (live state) + Postgres/Parquet (history) → FastAPI (WebSocket + REST) → a `lightweight-charts` chart that backfills history on load, then live-updates. Whale alerts flow detector → `alerts.whales` → both `/ws/whales` (the right panel's whale list) and the Telegram bot (your phone). EMA 20, 50 and 200 are computed in Spark on every chart timeframe (candles → `market.candles.1m` → `applyInPandasWithState` → Postgres + Redis + Gold) and reach the chart with every page of history and live; every other indicator, and any other EMA length, is still computed in the browser (`frontend/src/indicators/`). History the live socket never saw comes from `backfill/`: a year of Binance REST klines into `candles_1m` (and Bronze), the last 30 days of aggTrades into Bronze and the footprint, safe to rerun, after which the live indicator job rebuilds itself. The **volume footprint** (buy and sell volume per $1 price level per minute) is computed live in Spark alongside the candles (→ Postgres's `footprint_1m` + Redis + Gold), its history comes from the backfill's aggTrades, and the chart draws it over the candles on 1m to 1h once zoomed in, with fixed-range and anchored volume profile tools on every timeframe. `tests/` holds a pytest suite over real Kafka, Redis and Postgres, the frontend has Vitest tests, and GitHub Actions runs both on every push. Not built yet: the other planned top-level folders (`data_quality/`, `observability/`).

`docs/architecture.html` maps the whole pipeline: ten left-to-right stages, four lanes (hot path, Medallion lakehouse, whale alerts, order book), every component and every data movement, each marked built / roadmap / suggested, plus a table of all 83 movements. One self-contained file — open it in a browser (it sketches with rough.js from a CDN and falls back to plain boxes offline). When a stage lands, change that node's `status` in the file's `NODES` array rather than redrawing anything; a component the diagram doesn't have yet is a new `NODES` entry and its movements new `EDGES` entries (layout is automatic; an edge that would cross boxes takes a `route` — see `routePoints()`).

```bash
pip install -r ingestion/requirements.txt

pip install -r backend/requirements.txt     # fastapi, uvicorn, redis, psycopg, aiokafka

pip install -r tests/requirements.txt       # pytest & co., for scripts/test.sh
```

## Architecture

**`config/settings.py`** is the one config module every Python service imports (`from config.settings import ...`): `SYMBOLS`, the Kafka broker, Redis host/port, the Postgres DSN, the Parquet `DATA_ROOT`, the whale threshold, the CORS origins, Binance's REST URL (for the backfill), and the Telegram bot's token, chat id and API URL (the token and chat have no defaults: they come from the environment or `.env`, never from git). Each can be overridden by a `DSVIEW_*` environment variable, and the defaults match `docker-compose.yml`, so local dev needs none. The pipeline contract lives there too and is deliberately not overridable, because producers and consumers must agree on it: the Kafka topic names, the chart `TIMEFRAMES` (streaming buckets indicators by the same ids the backend serves; `frontend/src/lib/timeframes.js` must match, and a Vitest test checks it), `SERVER_EMA_LENGTHS`, the EMA lengths Spark precomputes (one `candle_indicators` column each; `frontend/src/indicators/server.js` must match, also checked), and the footprint's `FOOTPRINT_PRICE_STEP` ($1: the level width `footprint_1m` stores) and `FOOTPRINT_TIMEFRAMES` (1m to 1h; `frontend/src/footprint/levels.js` must match both, checked). New deployment config (hosts, paths, credentials, thresholds) goes there, never into a module constant; a constant that tunes one module and is explained in place (the Redis key TTL, watermark delays, the REST page limits) stays in its module. It's dependency-free on purpose: every service imports it, so it can't pull in a library one of them doesn't install.

The ingestion layer follows a deliberate SRP/OCP/DIP split — read `ingestion/base_client.py`'s and `ingestion/producer.py`'s module docstrings before changing the wiring, they explain the reasoning:

- **`schema.py`** is the canonical contract. Every exchange adapter normalizes its wire format into `TradeEvent` / `DepthUpdate` (union type `MarketEvent`) before anything else sees the data. `kafka_topic_for()` is the single place that maps an event type to a Kafka topic — add new topics here, not per-caller (the topic name itself goes in `config/settings.py`, because `streaming/` subscribes to the same names and must not import from `ingestion/`).
- **`base_client.py`** defines `BaseExchangeClient`, an abstract WebSocket client that owns connection lifecycle and exponential-backoff reconnect. It knows nothing about Kafka or any specific exchange. Subclasses implement only `ws_url`, `build_subscription_message()`, and `parse_message()`. It depends on an injected `on_event` async callback rather than importing the producer directly — this is what keeps ingestion testable without a broker.
- **`binance_client.py`** is the reference implementation of that contract (first and currently only exchange adapter). `Exchange` enum in `schema.py` already anticipates Coinbase and Kraken — new exchanges should be added the same way: a new subclass of `BaseExchangeClient`, no changes needed to `base_client.py`.
- **`producer.py`** (`MarketDataProducer`) is the sole boundary between ingestion and Kafka — a thin async wrapper over `AIOKafkaProducer`. Exchange clients never touch it directly; they only ever call the `on_event` callback they were constructed with. Partitions by symbol (`event.symbol` as the Kafka key) to preserve per-instrument ordering for downstream windowed aggregations in Spark.
- **`main.py`** is the only file that imports both a concrete exchange client and the producer, wiring them together and running clients concurrently under asyncio with graceful SIGINT/SIGTERM shutdown. It reads `SYMBOLS` and `KAFKA_BOOTSTRAP_SERVERS` from `config/settings.py`.

When extending ingestion: normalize to `schema.py` types, keep new exchange adapters as `BaseExchangeClient` subclasses in their own file, and don't let Kafka-specific concerns leak upstream of `producer.py`.

`streaming/` consumes what `ingestion/` publishes, and splits per-event vs. windowed work into two different execution models rather than forcing everything through Spark:

- **`jobs/whale_detector.py`** is a plain asyncio `aiokafka` consumer — flagging one trade against a size threshold needs no windowing or cross-event state, so Spark's startup/resource cost would be pure overhead here. Each trade at or over `WHALE_THRESHOLD_USD` is logged and handed to an injected `on_whale` callback (the same DIP as ingestion's `on_event`, so detection runs without a broker); `_main()` wires that callback to **`alert_publisher.py`** (`AlertPublisher`), the one place `streaming/`'s plain-Python side produces to Kafka (Spark jobs write through Spark's own Kafka sink: see `candle_topic.py`), which publishes it to `alerts.whales` keyed by symbol. The alert's JSON shape is documented in the detector's docstring — it's the contract `/ws/whales` forwards as-is and the Telegram bot consumes. Delivery is best-effort (offsets auto-commit, so a crash can repeat an alert and a publish that fails after the producer's retries is logged and skipped); consumers dedupe on `(exchange, trade_id)`. Shutdown is bounded: `stop_within()` gives the consumer and then the publisher 5 s each to close, because with the broker down aiokafka's `consumer.stop()` either retries its final commit forever (Ctrl+C used to hang for good) or raises a `CancelledError` of its own making. It runs the close as a task of its own rather than under `asyncio.wait_for()`, so that leaked `CancelledError` reads as a failed close instead of cancelling the shutdown into a traceback; any new Kafka consumer's shutdown should go through it too.
- **`trades_source.py`** (`read_trades_stream()`) and **`candle_windowing.py`** (`build_candles()`) are the shared Kafka-read/parse and tumbling-window-aggregation steps, factored out so `jobs/candle_aggregator.py` and `jobs/storage_writer.py` can't drift against each other — both consume `market.trades.raw` and compute the exact same OHLCV logic, just with different output modes and sinks (see below). `schemas.py` declares the raw JSON wire shape as a Spark `StructType` (all `StringType`, cast to real types after `from_json`) rather than importing `ingestion/schema.py`'s pydantic models — same reasoning `whale_detector.py` documents: once an event is on the wire it's just JSON, so a consumer shouldn't share Python types with the producer across the topic boundary. `spark_session.py` centralizes the SparkSession config (including the `spark.jars.packages` coordinate for the Kafka connector, version-pinned to the installed pyspark) so every job shares one config instead of drifting. It also sets Spark's session time zone to UTC (so `to_json()` and pandas UDFs see UTC, not the laptop's IST) and points Spark's Python workers at the running interpreter (`PYSPARK_PYTHON`): the indicator job's pandas UDF runs in those workers, which import streaming's modules by bare name — a job run from `streaming/` has it on their path; the tests add it to `PYTHONPATH`.
- **`jobs/candle_aggregator.py`** runs the windowed aggregation in `outputMode("update")` for **live serving**: writes console + `redis_sink.py` + `postgres_sink.py` + the `market.candles.1m` topic inside one `foreachBatch` (Structured Streaming has no built-in Redis/Postgres sink, so one streaming query does all four rather than separate queries against Kafka; the batch is persisted for them).
  - **`candle_topic.py`** owns `market.candles.1m` both ways: `publish_candles()` writes each batch's candles (keyed by symbol, valued as the same JSON Redis gets — decimals as strings, times in UTC) and `read_candles_stream()`/`parse_candles()` read them back with their Kafka offset. The topic exists because Spark 3.5 won't run `applyInPandasWithState` after a streaming aggregation in the same query (update and append mode alike), so the indicators can't chain onto `build_candles()` directly. Order matters — the indicator engine relies on a symbol's candles arriving as produced — so each batch is written sorted, from one task, one request in flight. `ensure_candles_topic()` creates it if missing: Spark's Kafka source fails a query outright on an unknown topic.
  - **`redis_sink.py`** (`CandleRedisSink`) — analogous to `producer.py`'s role for Kafka: nothing else touches `redis` directly. Every write goes to two places: a TTL'd SET (`candle:{symbol}:{timeframe}`) so a newly-connected client can fetch current state immediately, and a PUBLISH (`candle_updates:{symbol}:{timeframe}`) so already-connected clients get pushed each update.
  - **`postgres_sink.py`** (`CandlePostgresSink`) — upserts into Postgres's `candles_1m` table (`ON CONFLICT (symbol, window_start) DO UPDATE`) on every batch. Upserting repeatedly rather than writing once-on-close is deliberate: update mode never signals "this window is finalized," but repeated upserts converge to the correct final row once the watermark stops emitting updates for that window — no separate close-detection needed.
  - **Timestamps**: PySpark's `collect()` returns `TimestampType` as a *naive* datetime in the driver's local timezone (IST on the dev laptop), not UTC. `_row_to_candle()` converts `window_start`/`window_end` to aware UTC before either sink sees them — any future `foreachBatch` job writing timestamps out must do the same. Skipping it once left Postgres storing every candle 5h30m in the future and the chart's backfilled history misaligned with its live updates.
  - **The live footprint** (Phase 3b) is a second query in the same application (`build_footprint_query()`; another Spark process would cost another JVM), also update mode, trigger 5 s. **`footprint_windowing.py`** (`build_footprint()`) groups trades by symbol, 1-minute window and price level (`floor(price / FOOTPRINT_PRICE_STEP) * step`, so $1 rows named by their lower bound) and sums `quantity` by taker side into `buy_volume`/`sell_volume`; it uses `candle_windowing`'s window length and watermark, not copies, so a minute's levels add up to its candle volume (for the minute still forming the two queries can be a batch apart; they agree once it closes). The one exception is the minute the app starts in: each query resolves Kafka's "latest" offset as it starts, a moment apart, so that minute can differ slightly; a backfill rerun replaces it with the exchange's. Its foreachBatch writes Postgres first (`FootprintPostgresSink`: `executemany` upsert of every level the batch changed into `footprint_1m`, one transaction), then Redis (`FootprintRedisSink`): update mode only hands over changed levels, so each live minute's levels collect in a hash (`footprint_levels:{symbol}:1m:{epoch}`, TTL 180 s) read back in the same pipeline, and every touched minute goes out whole — PUBLISH `footprint_updates:{symbol}:1m` and, for the newest minute only (a late revision of an older one leaves it), SET `footprint:{symbol}:1m` (TTL 120 s). A whole grid per message means no message depends on the ones before it. Numbers in those messages are plain decimal strings (`redis_sink.plain_decimal()`: "97000", never "9.7E+4").
- **`jobs/storage_writer.py`** runs five *separate* streaming queries in one Spark application (one JVM, one Kafka-connector resolution, instead of five) for the Bronze/Silver/Gold Parquet layers under `storage/data/` (gitignored). `start_storage_queries(spark, data_root)` starts them (the tests point it at a temporary directory); `main()` adds the session and the wait:
  - **Bronze** (`storage/data/bronze/trades/`) — `market.trades.raw` written append-only, exactly as `trades_source.py` parses it. The durable replay/backtest source (feature roadmap item 4).
  - **Silver** (`storage/data/silver/trades/`) — Bronze deduplicated by `trade_id` within a watermark window. Ingestion's pydantic validation already guarantees well-formed data, so dedup + a compacted layout is Silver's whole job for now.
  - **Gold** (`storage/data/gold/candles_1m/`) — the *same* `candle_windowing.build_candles()` aggregation as `candle_aggregator.py`, but in `outputMode("append")` instead of `"update"`. Append mode only emits a window once its watermark has passed — exactly once per finalized candle — which is what makes it safe to write to an append-only Parquet sink; writing `candle_aggregator.py`'s update-mode output to Parquet instead would pile up duplicate, progressively-refined rows per window. This is why Gold can't just consume `candle_aggregator.py`'s stream and needs its own query built from the shared aggregation function instead.
  - **Gold indicators** (`storage/data/gold/indicators/`, by symbol and timeframe) — `indicator_state.compute_indicators()` in `final_only` mode over Gold's own candles, read back as a Parquet file stream: Gold derived from Gold, each bar written exactly once, when final. Its read schema puts the partition column (`symbol`) last, the order Spark gives such a source itself: Spark 3.5's streaming Parquet source misreads a user-given schema with a partition column anywhere else (it crashed the JVM with a SIGSEGV in Murmur3 hashing). To rebuild, delete both `_checkpoints/gold/indicators` and `gold/indicators`.
  - **Gold footprint** (`storage/data/gold/footprint_1m/`) — `build_footprint()` in append mode, each finalized minute's levels written once, so any past footprint or volume profile can be rebuilt without replaying Bronze. Like Gold's candles it holds only what the live stream finalized; the backfill's footprint history goes to Postgres alone. Read back with pyarrow its `window_start` is a naive timestamp (Spark's Parquet writer), UTC in fact.
- **`jobs/indicators.py`** computes EMA 20, 50 and 200 on all six timeframes (Phase 2's kickoff decision, in `docs/ROADMAP.md`) from `market.candles.1m`, for live serving:
  - **`indicator_engine.py`** (`IndicatorEngine`) is the computation, plain Python with no Spark: one engine per symbol rolls 1m candles up into each timeframe's epoch-aligned buckets (keeping only each bucket's latest close) and steps the EMAs exactly as `frontend/src/indicators/math.js`'s `ema()` does, in the same floating-point operation order, so the two agree bit for bit (golden tests run math.js itself through `tests/js/ema_reference.mjs`). The live input re-sends each minute as it forms and can revise the previous one after the next has started, so a bar stays **provisional** until a candle two minutes newer proves it can't change (`LIVE_SETTLE_MINUTES`, valid while `candle_windowing.WATERMARK_DELAY` stays under a minute — a test checks), and only then joins the running state. `drain()` returns every bar whose value may have changed (the changed bar and every bar after it); `final_only=True` returns each bar once, when final. State goes to and from JSON, and a state saved by another version or configuration is refused (`StateMismatch`), never misread.
  - **`indicator_state.py`** (`compute_indicators()`) is the Spark side: `groupBy("symbol").applyInPandasWithState(...)`, with the engine's JSON as the state, kept in the query's checkpoint. The first time a live query sees a symbol it **warms up** from every 1m candle in `candles_1m` before that batch (`postgres_sink.read_minute_closes()`), so the whole stored history gets server values, not just bars since the job's first run.
  - The foreachBatch writes every changed bar to Postgres (`IndicatorPostgresSink`, `executemany` upsert into `candle_indicators`, one transaction per batch) and Redis (`IndicatorRedisSink`: SET `indicators:{symbol}:{timeframe}` with the newest bar, PUBLISH `indicator_updates:{symbol}:{timeframe}` for at most a series' newest three bars per batch, so a warm-up rewriting history doesn't flood the charts). Bar times are cast to Unix seconds in Spark before `collect()`, which sidesteps the naive-local-datetime trap above.
  - **Rebuilds after a backfill**: the state is `{"revision", "engine"}`, the revision being the symbol's `candle_revisions` counter the engine was built from. Every batch reads the current one (`postgres_sink.read_candle_revision()`, one indexed lookup; 0 without a row or without the table), and a symbol whose revision moved is warmed up again from `candles_1m` as if new, its whole history's rows written with that batch (~25 s for a year). So the job never needs a restart after a backfill. A Phase 2 checkpoint holds the engine's state bare and reads as revision 0. The warm-up reads `candles_1m` before the batch's first minute and relies on the batch for the rest, which holds because `candle_aggregator.py` upserts `candles_1m` before it publishes each candle.
  - **Checkpoint**: `DATA_ROOT/_checkpoints/indicators` holds the EMA state and the topic offsets, so a restart resumes exactly and replays candles published while the job was down. Deleting it rebuilds every symbol from `candles_1m` (needed after changing `SERVER_EMA_LENGTHS`, or if the job stayed down past the topic's retention, where Spark stops with a data-loss error rather than skip candles); a backfill doesn't need it (see above).
- `storage/ddl/gold_candles.sql` defines the `candles_1m` Postgres table `postgres_sink.py` upserts into, `storage/ddl/indicators.sql` the `candle_indicators` table (PK `(symbol, timeframe, window_start)`, one `DOUBLE PRECISION` column per EMA length so the browser gets Spark's doubles exactly), `storage/ddl/candle_revisions.sql` a counter per symbol that the backfill raises when it changes `candles_1m`'s history, and `storage/ddl/footprint.sql` the `footprint_1m` table (PK `(symbol, window_start, price)`, `buy_volume`/`sell_volume` `NUMERIC(38,18)`; written by the live footprint query and the backfill); apply them via `storage/init_db.py` (see Setup above). Not using a migration tool yet: every file is `CREATE ... IF NOT EXISTS`, so a column added to an existing table needs an `ALTER TABLE` by hand.

`alerts/` is the Telegram bot, the last leg of the whale lane (`alerts.whales` → your phone). Like ingestion, each concern is its own module and only the entrypoint wires them together:

- **`telegram_bot.py`** (`WhaleTelegramBot`) reads `alerts.whales` in its own consumer group, `dsview-telegram-bot` (so it resumes after a restart; its first-ever start begins at the end of the topic). Delivery is **at-least-once**: offsets are committed by hand, and `_commit()` never commits past a whale still held — waiting for its group to close, or for Telegram to come back — so a crash re-reads it instead of losing it. Repeats are ignored on `(exchange, trade_id)` for the last 10,000 whales. Ctrl+C sends the open group at once; each shutdown step gets 5 s (`stop_within()`, as in the detector). `main()` refuses to start without `DSVIEW_TELEGRAM_BOT_TOKEN` and `DSVIEW_TELEGRAM_CHAT_ID`.
- **`whale_batcher.py`** (`WhaleBatcher`) implements the kickoff decision "whales within 10 seconds of each other share one message": a gap rule on the trades' own `event_time`, so a backlog read after a restart groups the way it happened live. A group is sent when a whale arrives that doesn't fit, after 10 s with no new whale, after 60 s of a continuous burst, or at 20 whales (far under Telegram's 4096-character limit). Pure and clock-agnostic — the caller passes `now` — so its tests need no waiting. A lone whale reaches the phone about 10 s after it trades.
- **`whale_card.py`** formats each whale as the decided three-line card (`🐋 BUY · BTCUSDT` / `$242.5K — 2.5 @ 97,000.10` / `Binance · 10:16:57 UTC`), numbers the way the right panel shows them, and `parse_time()` reads every timestamp shape the pipeline writes — Python 3.10's `fromisoformat()` rejects a `Z` suffix, which pydantic writes on every trade.
- **`telegram_client.py`** (`TelegramClient`) is the one place that talks to the Bot API. Sends are spaced 3 s apart (a group chat's 20/minute), a 429's `retry_after` is honoured, network errors and 5xx retry with backoff (1 s → 60 s) for as long as Telegram is down, other 4xx are logged and dropped, and `check()` (getMe + getChat) fails fast on a wrong token or chat. **The token is part of every Bot API URL**: nothing logs a URL or an httpx exception's text, and httpx's own per-request INFO logging is switched off — keep it that way.

`backfill/` is the history backfill (Phase 3a), a one-off, re-runnable job rather than a stream, plain asyncio (no Spark: paging a REST API is I/O-bound). As in ingestion, each concern is its own module and only the entrypoint wires them:

- **`binance_rest.py`** (`BinanceHistoryClient`) is the one place `backfill/` talks to Binance: `klines()` (1m, weight 2, 1000 a page) and `agg_trades()` (weight 4, 1000 a page; the first page found by time an hour's window at a time, the rest by `fromId`), each yielding pages already normalized to plain columns named as in Bronze. Rate limits: a `WeightBudget` shared by every concurrent request, a fixed window per wall-clock minute (Binance's own) capped at half the 6000 limit and kept in step with each response's `X-MBX-USED-WEIGHT-1M`; a 429 pauses everything for its `Retry-After` (not counted as a failed attempt), a 418 (IP ban) stops the run, 5xx and network errors retry with backoff 1 s → 30 s up to 8 attempts, any other 4xx fails at once with Binance's message. An aggregate trade is every fill of one taker order at one price, so per-price buy/sell volume is exact (all the footprint needs), but its ids are a different series from the live stream's trade ids.
- **`bronze_files.py`** owns Bronze's two backfilled datasets, `bronze/klines_1m` and `bronze/agg_trades`, one Parquet file per symbol and UTC day under Hive-style `symbol=`/`date=` directories (so Spark discovers both as columns; decimals `(38,18)` and UTC microsecond timestamps, as the live Bronze). They are deliberately not `bronze/trades`: that is a Spark streaming file sink whose readers list files from its `_spark_metadata` log, so a file written there by anything else is invisible, and its rows are individual trades that must never be summed with aggregates. Each day is written to a hidden temporary file (Spark skips dot-names) and renamed into place once complete; its Parquet metadata records the span it covers (`coverage()`), which is how a rerun knows what it already has.
- **`candle_store.py`** (`CandleStore`) is the one place `backfill/` touches psycopg: `upsert_candles()` writes a day's klines into `candles_1m` through COPY (an Arrow-written CSV, so a year takes seconds) into a temporary table and an upsert that rewrites a row only when a value differs (`IS DISTINCT FROM`; NUMERIC compares by value), returning how many rows changed and the oldest; zero-trade klines are skipped, since live never makes such a candle. The exchange's candle replaces a live one for the same minute: a live candle can only be short of trades. `bump_revision()` raises the symbol's `candle_revisions` counter. `replace_footprint()` makes `footprint_1m` hold exactly a span's rows from the exchange: COPY into a temporary table, delete the span's levels the exchange doesn't have, upsert the rest `IS DISTINCT FROM`, so live minutes are replaced whole and an unchanged reload writes nothing (no revision: nothing derived from the footprint keeps state). It refuses to start, with the fix in the message, if Postgres lacks any of the three tables.
- **`footprint_rows.py`** (`footprint_table()`) is the footprint's history: a day of Bronze aggTrades as `footprint_1m` rows, minute and level bucketed exactly as `streaming/footprint_windowing.py` does live, in pyarrow (~0.6 s per million trades, no JVM). Levels are floored per distinct price in Python's `Decimal`: Arrow's decimal division overflows at (38, 18). A Spark test checks the two agree on the same trades.
- **`history_backfill.py`** (`HistoryBackfill`, `main()`) runs both lanes per symbol concurrently, a UTC day at a time, newest day first: candles (two days at once) and aggTrades (`--concurrency`, four days at once). A run stops at the minute that closed `SETTLE_MINUTES` (2) ago, by when the live pipeline has finished that minute too. A day whose Bronze file already covers its span is skipped (aggTrades) or reloaded from the file into `candles_1m` (candles: free when nothing changed, and it restores an emptied table); every other day is fetched, candles going to Postgres before Bronze, so a Bronze file also means its candles are in. Every aggTrades day, fetched or skipped, is then loaded from its file into `footprint_1m` (only the run's span of it: a file can cover more), so reruns restore an emptied table too. If any candle changed, the revision is bumped as the run ends, even a failed or interrupted one. The first failure cancels the rest (`_all_or_nothing()`), and a half-fetched day leaves no file. Gold is untouched: Gold holds what the live stream finalized, and filling it from Bronze's history belongs with replay (Phase 4).

`backend/` is a FastAPI service with live push (candles from Redis, whale alerts from Kafka) and a historical-read side:

- **`redis_client.py`** (`CandleRedisReader`) is the read-side counterpart to `streaming/redis_sink.py` — the sole place `backend/` touches `redis`. `get_latest()` reads the cached SET (for a client's initial state); `subscribe_updates()` is an async generator over the PUBLISH channel; `get_latest_indicators()`/`subscribe_indicator_updates()` and `get_latest_footprint()`/`subscribe_footprint_updates()` do the same for the indicator and footprint keys and channels.
- **`routers/ws.py`** exposes `/ws/candles/{symbol}`: sends the current cached candle on connect, then forwards every subsequent pub/sub update until the client disconnects; if Redis is unreachable it closes the socket with 1011.
- **`routers/push.py`** (`push_until_disconnect`) is how every WebSocket route pushes: it runs the route's push loop alongside a `receive()` that watches for the client leaving, and cancels the loop as soon as it does. A server that only sends notices a closed connection when its next send fails, so without this a closed tab kept its Redis subscription (or Kafka consumer) until the next candle (or whale) — forever when the source is quiet, which also hung `uvicorn --reload` at "Waiting for background tasks to complete". New WebSocket routes should push through it too.
- **`postgres_client.py`** (`CandleHistoryReader`, `FootprintReader`) is the read-side counterpart to `streaming/postgres_sink.py` — the sole place `backend/` touches `psycopg`/Postgres. One connection per request for now (dev request volumes only; a pool is a documented future TODO, not built prematurely).
- **`routers/candles.py`** exposes `GET /candles/{symbol}?timeframe=1m|5m|15m|1h|4h|1D&limit=N&before=<ISO timestamp>`: candles oldest first (chart order); `before` pages backwards for the chart's scroll-back. Only `candles_1m` is stored — bigger timeframes are rolled up at query time by `postgres_client.py`'s `date_bin()` query (its comment explains why capping the scan at `limit × minutes-per-bucket` rows never returns a truncated bucket, and why open and close come from each bucket's first and last minute by primary key rather than an ordered aggregate: with a year of history a page of 1D bars rolls up 432,000 rows, which `array_agg(... ORDER BY ...)` sorted on disk in ~0.8 s; now ~0.2 s). Buckets are epoch-aligned, the same alignment `frontend/src/lib/timeframes.js` uses to roll live candles up; the two `TIMEFRAMES` lists must match. Each candle carries an `indicators` object (`{"ema_20", "ema_50", "ema_200"}`, null where Spark has no value), LEFT JOINed from `candle_indicators` on the same bar start for the requested timeframe, so every page of history (scroll-back included) brings its own values. This is a genuinely different data path from `ws.py` — it never touches Redis, which has no history to serve.
- **`routers/indicators.py`** exposes `/ws/indicators/{symbol}?timeframe=…`: the newest bar's cached indicator values on connect, then every bar Spark changes (usually the bar in progress, now and then a late revision of the one before — clients place each by its `window_start`). Per timeframe, unlike `/ws/candles`: an EMA on 5m bars can't be derived from the 1m one. Pushes through `push.py`; 1008 for an unknown timeframe, 1011 if Redis is unreachable.
- **`routers/footprint.py`** exposes the footprint. `GET /footprint/{symbol}?timeframe=1m|5m|15m|1h&start=&end=&row_size=`: every bar from `start` to `end` (default now; both widened to whole bars, at most 500 bars), each `{"window_start", "levels": [[price, buy_volume, sell_volume], ...]}` with prices ascending and numbers as plain decimal strings; `FootprintReader` merges `footprint_1m`'s $1 minutes into the bar (`date_bin()`, epoch-aligned like candles) and the row size (`floor(price / row) * row`, a multiple of the step, else 422) in one grouped query over the primary key's range (~5 ms for a screen of 1m bars, ~0.2 s for 100 hourly ones over 30 days). `GET /footprint/{symbol}/profile?start=&end=&rows=24` (or `&row_size=`) sums a range into a volume profile in one scan — $1 levels first, then a row size picked from their spread (TradingView's "number of rows") — plus `first_minute`/`last_minute`, which minutes of the range have any footprint (~0.2 s for 30 days). `/ws/footprint/{symbol}`: the cached newest minute's grid on connect, then every grid Spark publishes, 1m only (the client rolls up and merges rows itself); pushes through `push.py`, 1011 if Redis is unreachable. 4h and 1D are refused (422): plain candles there, kickoff decision 4.
- **`kafka_client.py`** (`WhaleAlertReader`) is the sole place `backend/` touches `aiokafka`. `stream(backlog)` is an async generator: one consumer per call with **no consumer group** (each WebSocket reads every partition itself and commits nothing, so two tabs both get every alert), seeked `backlog` messages before the end, then live. It *subscribes* rather than `assign()`s: a bare aiokafka consumer never learns a topic's partitions (`partitions_for_topic()` stays `None` even for an existing topic), while a group-less subscription gets every partition assigned, including ones added later. If `alerts.whales` doesn't exist yet, that subscription's metadata request creates it (Redpanda auto-creates topics, as the detector's first publish would). Stop the consumer through `_stop()`, not `consumer.stop()` directly: while the broker is unreachable, aiokafka's `stop()` leaks a `CancelledError` from fetch requests it just cancelled, which would replace the real error and make the stream look cancelled instead of failed. One Kafka connection per open tab is fine at dev scale; a shared consumer fanning out to all sockets is the upgrade if that changes.
- **`routers/whales.py`** exposes `/ws/whales?backlog=N` (default 50, max 500): the last N alerts oldest first, then live ones, each the detector's alert JSON forwarded unchanged. Like `ws.py`, it pushes through `push.py`, so a closed tab releases its consumer at once rather than at the next whale. If the broker can't be reached while a connection starts up (at once if it refuses connections, after aiokafka's 40 s request timeout if it vanishes mid-startup), it closes the socket with code 1011 — clients should reconnect, and the backlog replays what they missed. A stream that's already running rides out broker outages. Nothing else in the backend depends on Kafka.
- **`main.py`** wires up all five routers, plus `CORSMiddleware` (allowing `CORS_ALLOWED_ORIGINS` from `config/settings.py`, by default `http://localhost:5173`, the Vite dev server) — REST, unlike WebSocket, is subject to browser CORS once frontend and backend are different origins/ports.

`frontend/` is a Vite + React app (plain JS, `.jsx`, no TypeScript):

- **`api/candles.js`** (`fetchCandles`) is the one client for `GET /candles/{symbol}`; **`lib/timeframes.js`** defines the timeframes and the epoch-aligned bucket math shared by history and live roll-ups.
- **`hooks/useCandleHistory.js`** fetches the newest page for the current symbol + timeframe — and returns an empty list until it arrives, never the previous timeframe's bars. Older pages are fetched by `CandleChart.jsx` itself on scroll-back.
- **`lib/reconnectingSocket.js`** (`openReconnectingSocket`) is the WebSocket every backend hook uses: it reconnects on every close it didn't ask for (a backend reload, a 1011 when Redis or Kafka is unreachable) with exponential backoff, 1 s doubling to 30 s; only a socket that stayed open 10 s resets the delay, so a dependency that's down — accept, then 1011 at once — isn't retried every second. Plain JS with an injectable WebSocket and timers, so it's tested without React.
- **`hooks/useLiveCandles.js`** owns the connection to `/ws/candles/{symbol}` (through `reconnectingSocket.js`) and exposes the latest parsed 1m candle as React state. After a backend restart it resumes with the minute in progress (the backend sends its cached candle on every connect); minutes that closed entirely during a longer outage aren't filled in until a reload — a Phase 6 task in `docs/ROADMAP.md`.
- **`hooks/useWhaleTrades.js`** owns the connection to `/ws/whales` and returns `{ trades, status }`: every symbol's whale alerts newest first (the detector's alert JSON as-is, capped at the 50 a connect replays) and `"connecting" | "live" | "reconnecting"`. Trades are deduplicated on `(exchange, trade_id)`, which is what makes reconnecting (through `reconnectingSocket.js`) safe: each connect replays the backlog, so a reconnect fills in what was missed without repeating what's shown. `parseTrade()` parses each message *before* the state update and ignores (and logs) anything that isn't a JSON object — parsed inside the updater, one bad message on the topic unmounted the whole app, and the backlog replay brought the blank page back on every reload.
- **`config.js`** holds the backend's HTTP and WebSocket base URLs — the one place they're defined; every client of `backend/` imports them.
- **`hooks/useTimeframeCandle.js`** rolls that 1m stream up into the live candle for the selected timeframe (the backend only streams 1m). It keeps the current bucket's 1m candles in a Map and re-aggregates on every update — the same 1m candle is re-sent many times while it forms, so running totals would double-count — and seeds the Map over REST first, so a bucket already in progress at page load isn't missing its earlier minutes.
- **`components/chart/CandleChart.jsx`** wraps `lightweight-charts` v5 (TradingView's open-source rendering library — unrelated to any "TradingView API," see the Data sources section below; v5's API is `chart.addSeries(CandlestickSeries)`, not v4's `addCandlestickSeries()`) and takes both `history` and `candle` props: `history` seeds the chart once via `setData()` (standard lightweight-charts backfill pattern), then `candle` keeps it live via `series.update()`. `update()` specifically — not `setData()` again — for the live path: the backend re-sends the *same* `window_start` repeatedly while a candle is still forming, and `update()` replaces a bar with a matching timestamp instead of duplicating it, while a new timestamp appends a new bar — exactly matching how `candle_aggregator.py` emits data. `update()` throws on a bar *older* than the last one, so live candles older than the last bar (late-trade refinements of an already-superseded window) are dropped rather than passed through. Scrolling to near the oldest loaded bar fetches the page before it and prepends it, merged with `series.data()` rather than the original history array so bars appended live since load survive — but only once the first history page is in (the live candle can land first, and paging back from that lone bar fetched the very page still loading), keeping only bars older than the chart's first. `App.jsx` keys the chart by symbol + timeframe, so a switch mounts a fresh chart instead of resetting refs by hand.
- **`components/chart/chartTheme.js`** reads `styles/theme.css`'s CSS variables into chart/series options — the chart draws on a canvas, which can't use CSS variables, so this keeps `theme.css` the only place colours are defined. Keep `attributionLogo` on: lightweight-charts' license requires a tradingview.com link on the page, and that option provides it.
- **`components/chart/Legend.jsx`** is the top-left O/H/L/C readout, driven by the chart's `subscribeCrosshairMove` (latest bar when the crosshair is off the chart).
- **`drawing/`** is the drawing tools. `DrawingLayer.js` is a single lightweight-charts series primitive that renders every drawing (plus axis labels and the hover cursor); `DrawingController.js` handles interaction — placing via `subscribeClick`/`subscribeCrosshairMove`, selecting/dragging via a capture-phase `mousedown` on the chart's wrapper that stops the press before lightweight-charts (which listens for mouse events, not pointer events) can pan, and Esc/Delete — skipping any key `lib/keyboard.js`'s `isChartKey()` rejects: typed into a field or dialog, or already handled (`preventDefault()`) by something else, which is how an open toolbar menu keeps its Esc from also leaving the tool. `tools.js` holds each tool's anchor count, draw and hit-test, all in pixels. Rays and extended lines store only their two anchors and are run to the pane's edge afresh on every draw; the trend-angle and info-line angles are on-screen angles, so they change with zoom (as TradingView's do). The `measure` key is the toolbar's "Date and price range" — renaming a tool's key orphans drawings already saved under it. A tool can also define `create` (sizes itself from one click), `moveHandle` (constrained or coupled handles), `handles` (where its handles sit) and a function `priceAxisLabel` — see `tools.js`'s header. A long/short position is four points kept in step (entry, target, stop, end), so dragging the whole drawing needs no special case; its target and stop move vertically only and never cross the entry. `barData.js` gives tools the candles plus volume (`bars.between(from, to)`, read fresh on every call, so scroll-back pages and the live bar are included). Anchored VWAP sums from the bar its anchor falls in, on any timeframe, sharing its running sum with the VWAP indicator (`indicators/math.js`), and draws nothing while that bar isn't loaded rather than a wrong average from a later one. Drawings are stored per symbol in `localStorage` (`drawingStore.js`) as time/price, never pixels; `coordinates.js` places a time relative to the bar `timeToIndex(time, true)` returns (`index + (time − barTime) / barSeconds`), so a drawing made on one timeframe lands correctly on every other. `App.jsx` owns the active tool and magnet state; the controller resets the tool to the crosshair itself after each drawing, not just via React, so a click arriving before React re-renders isn't handled with the old tool.
- **`indicators/`** is the indicators: SMA, EMA, Bollinger Bands and VWAP over the candles; RSI and MACD each in their own pane. `math.js` holds the formulas as pure functions; `definitions.js` describes each indicator (params, pane, lines) and its `compute()` — the seam between the browser and Spark: an EMA at one of `server.js`'s `SERVER_EMA_LENGTHS` takes the server's values whenever the server has any for the loaded bars, and math.js's otherwise (any other length; the indicator job not running) — never a mix within one line, since the two seed differently and a line switching bar by bar would jump. **`server.js`** holds those lengths, a per-chart store of server values by bar time (filled from every history page's `indicators` and from live messages, which win over a page fetched a moment earlier), the `server` input `compute()` reads, and the `/ws/indicators` message parser. **`hooks/useLiveIndicators.js`** owns that socket (through `reconnectingSocket.js`, only while the chart shows a Spark-computed indicator) and hands each message to a callback rather than React state: one Spark batch can send two before React renders. The legend's name tooltip says "Computed by Spark" or "Computed in the browser". `IndicatorManager.js` (created by `CandleChart.jsx`, like `DrawingController.js`) owns the indicator series and oscillator panes, rebuilds them all on any list change rather than diffing, and recomputes from `candleSeries.data()` on every data change — `setData()` after history loads or a scroll-back page is prepended, `update()` of the last point on live ticks. `hooks/useIndicators.js` persists the list to `localStorage`; each instance keeps the colour slot it got when added, so removing one never repaints the others. Colours are three validated hues (`--color-series-1..3` in `theme.css`, avoiding the hues that already mean up / down / drawings), then the same three dashed — so over-the-candles indicators cap at six. Legend rows (`components/chart/IndicatorLegend.jsx`) keep values in text colours with a coloured swatch beside each; an oscillator pane's legend is positioned from `pane.getHTMLElement()`.
- **`footprint/`** is the volume footprint (Phase 3b). `levels.js` holds the pure functions (levels merged into rows, minutes combined, the auto row size — the smallest of `ROW_SIZES` whose rows are `MIN_ROW_PX` (14) tall at the price zoom — a bar's point of control, delta and diagonal imbalances (buy at a row ≥ 3× sell one row below, and the reverse), a volume profile's 70% value area, cell number formatting) and the step and timeframes that must match `config/settings.py`. `FootprintStore.js` is one chart's data, plain JS: history bars per row size (a fetched range marks every bar loaded, empty ones included), live minutes at $1 per bar, a bigger timeframe's bar in progress seeded with its earlier minutes over REST before it replaces its history — `useTimeframeCandle.js`'s rule, live minutes winning. `FootprintManager.js` (created by `CandleChart.jsx` on 1m to 1h, like `IndicatorManager.js`) decides on every chart update what to draw: only once bars are `MIN_BAR_SPACING_PX` (48) apart (turning the footprint on zooms to 72 and narrows the right margin, restored when it's turned off), at the setting's fixed row size or the auto one, from the store, fetching any visible bar it lacks in one throttled request — so only bars on screen are fetched; it reports `{ state, rowSize }` for the legend's note. `FootprintLayer.js` is a series primitive on the candle series with zOrder `"normal"` (above the candles, below drawings and the crosshair): per bar a column that first paints over the candle it replaces (a bar without data keeps its candle), a slim candle on its left edge, rows split sell (left, red) and buy (right, green) tinted by size, numbers when they fit, the POC outlined, imbalances bold, the delta beneath. A primitive rather than `addCustomSeries`, so drawings, indicators, the crosshair legend and scroll-back keep working on the one candle series. **`api/footprint.js`** is the client for all three footprint endpoints; **`hooks/useLiveFootprint.js`** owns `/ws/footprint` (only while the footprint shows) and hands each minute to the manager through a callback, as `useLiveIndicators.js` does. **`hooks/useChartSettings.js`** persists the chart type (`"candles"` or `"footprint"`) and the footprint's row size (`"auto"` or dollars); the top bar's **`ChartTypeButton.jsx`** sets both through `ToolMenu` (which now also opens below a button, `placement="below"`, and takes `isChecked` for menus with a choice per section).
- **Volume profiles** are two drawing tools in `drawing/tools.js` (`fixed-range-volume-profile`, two anchors: from the first anchor's bar through the second's; `anchored-volume-profile`, one anchor: through the latest bar), drawn as a histogram on the range's left edge (buy then sell per row, longest 30% of the range's width), the 70% value area solid and the rest faint, the POC line across, totals beneath, and a note when the footprint's history starts after the range does. Their data is **`drawing/profileData.js`**, which DrawingLayer passes in every tool's context as `profiles`, next to `bars`: a synchronous `get(start, end, rows)` that returns the cached profile or starts the fetch and returns null, the landing redrawing the chart; a range reaching the bar in progress (`end` null) is refetched every 5 s while drawn. `DrawingController` now takes the chart's `symbol` for it.
- **`components/layout/`** holds the workspace around the chart — `TopBar`, `DrawingToolbar`, `RightPanel` (watchlist, plus the whale feed from `useWhaleTrades`, times in UTC like the chart's axis), `BottomBar` — placed by `App.jsx`'s CSS grid. Controls for features that don't exist yet are rendered anyway through `ToolbarButton`'s `notBuilt` prop (dimmed, inert, tooltip says "not built yet"); when a feature lands, drop `notBuilt` and wire `onClick` rather than adding a new button. `DrawingToolbar` groups tools TradingView-style: `drawingToolGroups.js` is the whole layout (groups → titled sections → tools, each with its icon and Alt-key shortcut; planned tools are `notBuilt` entries, same convention — when one lands, add it to `tools.js`'s `TOOLS` and drop the flag). `ToolGroupButton` shows each group's last-used tool (persisted by `hooks/useLastUsedTools.js`) with an arrow that opens `ToolMenu`, which is portalled to `<body>` because the toolbar scrolls and would clip it. Icons lucide lacks are drawn in `toolIcons.js` with lucide's `createLucideIcon` — never copy TradingView's artwork.
- **`components/ErrorBoundary.jsx`** wraps the chart, so a chart error shows a retry button instead of React unmounting the whole app to a blank page.
- Styling is CSS Modules (`*.module.css`, one per component) on top of the design tokens in `styles/theme.css`; icons come from `lucide-react`.
- **`App.jsx`** holds the UI state — timeframe, chart type and footprint rows (via `useChartSettings`), drawing tool, magnet, the indicator list (via `useIndicators`) and which indicator dialog is open — and hardcodes `SYMBOL = "BTCUSDT"` — symbol selection is future work, not implemented.


`tests/` is the pytest suite, run by `scripts/test.sh` (see Setup / running), against real Kafka, Redis and Postgres rather than mocks — offsets, consumer groups, pub/sub, upserts and Spark's Kafka source are where things actually break. Folders mirror the services (`tests/ingestion/`, `tests/streaming/`, …); `pytest.ini` puts each service folder on `sys.path`, the way running it from its own folder does, so tests import modules the same bare way the services do (`ingestion/` and `backend/` both have a `main.py`, so the backend tests load theirs by path). Conventions:

- **Never the dev stack.** Every service fixture fails unless `DSVIEW_KAFKA_BOOTSTRAP_SERVERS`, `DSVIEW_REDIS_PORT` and `DSVIEW_POSTGRES_DSN` are set, and `test.sh` clears every other `DSVIEW_*` variable. On the dev broker the suite's synthetic whales would reach the right panel and the real Telegram bot.
- **A symbol per test** (the `symbol` fixture): topic names are fixed, so tests share topics and tell their own messages, rows and keys apart by symbol.
- **Synthetic trades go through ingestion's real `MarketDataProducer`** (`trade_producer` fixture, `helpers.make_trade()`), so downstream tests read exactly what live ingestion publishes. A consumer starting at "latest" must be positioned before a test produces (`helpers.wait_until_positioned()`); a Spark query has pinned its offsets once `query.lastProgress` is set (its first, empty batch).
- **Telegram is `tests/fake_telegram.py`**, a stand-in Bot API that records messages and can fail on demand (429, 5xx, 400).
- **Binance REST is `tests/fake_binance.py`**, a stand-in for `/api/v3/klines` and `/api/v3/aggTrades` over a `SyntheticMarket` that is a pure function of symbol and time (its klines computed from its own trades, as Binance's are), so backfill tests compute every expected value themselves; it records requests and fails on demand (`fail_next()`, or `fail_matching()` for a predicate). The backfill tests run on a fake clock (`FakeTime`), so rate-limit and backoff waits cost nothing.
- **WebSocket tests disconnect by hand and wait for the handler to finish** before leaving the `with` block: TestClient cancels the app the moment the block exits, which uvicorn never does.
- Spark tests are marked `spark` (`-m "not spark"` skips them) and share one session; the conftest puts `streaming/` on the Python workers' `PYTHONPATH` (the indicator job's pandas UDF imports its modules by bare name). Running queries are fixtures in `tests/streaming/conftest.py`.
- **Golden tests** check Spark's EMA against the browser's own `math.js`: `helpers.math_js_ema()` runs `tests/js/ema_reference.mjs` with node, which rolls candles up with `lib/timeframes.js` and calls `ema()`, and the tests require exact equality on every bar of every timeframe — for the engine alone, from trades through both Spark jobs into Postgres, and for Gold. They skip if node isn't on PATH (CI has it).

Frontend tests are Vitest files next to the code they test (`frontend/src/**/*.test.js`), node environment, no DOM: pure functions and plain-JS modules only (hooks keep their logic in exported functions, like `addTrade()` and `parseTrade()`).

# DSView — Project Context

This section captures design decisions made before any code existed, so they don't
need to be re-derived or re-explained. `/init` can infer build commands and file
layout from the code itself — it can't infer *why* these choices were made, so keep
this section even as the codebase grows.

## What this project is

A real-time, multi-exchange crypto market data pipeline (starting with BTC-USD,
designed to extend to gold/XAU-USD later) that replicates TradingView's premium
features from scratch: volume footprint, whale tracking, and technical indicators.
Two goals: close a Kafka / Spark Structured Streaming skill gap, and produce
something genuinely useful for trading decisions.

## Data sources

- **Primary sources**: Binance, Coinbase Advanced Trade WebSocket, Kraken WebSocket v2
  — all exchange-native, real trade-level data (price, quantity, buy/sell side) plus
  order book depth. Build fully end-to-end on Binance first, then add Coinbase and
  Kraken as additional adapters behind the same interface.
- **Not using CoinGecko as a primary source** — it's an aggregator (blended price
  across exchanges, rate-limited REST/WS, no per-trade side or real order book), which
  makes it unusable for footprint or whale detection. May add it later purely as a
  slow-cadence source for market-wide context (e.g. BTC dominance).
- **No official TradingView data API exists.** Do not integrate any third-party site
  branded "TradingView API" — those are unofficial and not affiliated with TradingView.

## Feature roadmap (build in this order)

`docs/ROADMAP.md` is the execution plan built from this list: what's left, grouped into phases, each with its tasks, kickoff decisions and a definition of done. Work from it, and tick tasks there as they land.

1. **Whale tracking** — per-transaction size threshold filter, no windowing needed.
   Simplest, first end-to-end milestone.
2. **Technical indicators** — EMA/RSI on tumbling windows via Spark Structured Streaming.
3. **Volume footprint** — price-bucketed buy/sell volume within a candle. Hardest;
   needs careful price-bucket granularity choices.
4. **Later**: backtest, replay mode (reuse the live pipeline, feed it historical data
   at controlled speed), long/short ratio (needs Binance **Futures** API, not spot).
5. **Stretch goal**: order book heatmap / depth imbalance (needs order book state
   reconstruction, not just trades).
6. **Future phase, not yet planned in detail**: an AI layer using open-source Hugging
   Face models — FinBERT/CryptoBERT for sentiment, a Kronos-style time-series model
   for candlestick forecasting.

## Architecture

| Stage | Tech | Notes |
|---|---|---|
| Ingestion | Python WebSocket clients per exchange | Normalize into one canonical trade/depth schema before it hits Kafka |
| Message bus | Redpanda (Kafka-API-compatible) | Chosen over vanilla Kafka to save laptop resources during local dev — same client code either way |
| Stream processing (windowed) | Spark Structured Streaming, local mode | Indicators + footprint. Not containerized — run directly for faster iteration |
| Stream processing (per-event) | Plain Python consumer | Whale trigger — deliberately *not* Spark, no windowing needed |
| Storage | Bronze/Silver/Gold Iceberg or Parquet tables | Bronze = raw immutable, doubles as replay/backtest source |
| Serving | Redis | Latest real-time state (current candle, footprint grid) |
| Historical | Postgres (ClickHouse later if needed) | Queryable history for backtesting/UI load |
| Backend | FastAPI | REST for historical candles, WebSocket for live push from Redis pub/sub |
| Frontend | React + `lightweight-charts` (TradingView's open-source rendering library) | Candlestick/volume built in; footprint needs a custom panel |
| Alerts | Kafka topic → Telegram bot | Whale/anomaly notifications |
| Data quality | Great Expectations | Same tool used on an earlier project (Travel Tag pipeline) |
| Observability | Prometheus + Grafana | Add once core pipeline is stable, not needed day one |

## Deployment approach

- Get ingestion → Redpanda → Spark → Redis working directly on the host first —
  don't containerize prematurely, it slows down debugging early on.
- Once that chain works, wrap the stateful services (Redpanda, Redis, Postgres) into
  a single `docker-compose.yml`.
- Containerize FastAPI and the frontend later, once stable.
- Start entirely local (laptop). Move to cloud (AWS: MSK/EMR/ElastiCache/S3) later,
  incrementally — not decided in detail yet.

## Repo & code conventions

- **Flat Python project layout** at the repo root: `ingestion/`, `streaming/`,
  `backend/`, `alerts/`, `config/`, `tests/`, `scripts/`. Deliberately **not** using a
  Java-style wrapping root package (e.g. `src/dsview/`) — that convention is for
  publishable libraries, not a single standalone application repo like this one.
- `frontend/` (React) is a separate top-level folder, not part of the Python package
  tree.
- Working in PyCharm.
- Kafka/Redis/Postgres/table naming should be **symbol-based** (`trades.BTCUSDT`,
  `trades.XAUUSD`), not crypto-specific — the gold (XAU-USD) extension is planned to
  live in this same repo, reusing every downstream stage. Only the ingestion adapter
  and a per-asset feature flag (footprint/whale off for gold — spot gold's OTC market
  structure doesn't expose real trade-side volume) differ per asset.
